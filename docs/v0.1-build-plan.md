# NutrientLog v0.1: Build Plan (Draft 2)

Status: in progress (current milestone is tracked in the README). Draft 2 reordered the milestones to interleave backend and phone work (section 7).

## 1. Goal of v0.1

The smallest app that proves the foundations work end to end: **phone → API → database → back to phone**, with the structure everything later will sit on.

**In scope**
- Onboarding survey → calorie target
- Search USDA foods, or enter a food manually
- Log a food in grams or a named serving
- Home screen: "calories remaining" for today
- Anonymous user, data stored in Postgres
- Docker Compose (API + Postgres) and GitHub Actions CI

**Out of scope (later versions)**
Editing/deleting entries, meals, recipes, charts, weight log, AI, workouts, quest, themes, notifications, barcode scan, macros screen.

Note: v0.1 has no workouts, so the "eat back" setting doesn't exist yet. The calorie target is just the base target.

## 2. Prerequisites (one-time setup)

- [ ] GitHub account and Git installed
- [ ] Python 3.12+ and a way to manage virtual environments
- [ ] Node.js (LTS) and npm
- [ ] Docker Desktop (needs a few GB of disk; this is the main storage cost)
- [ ] A code editor (VS Code recommended)
- [ ] Expo Go installed on the iPhone 11
- [ ] Computer and phone on the same Wi-Fi network
- [ ] Free USDA FoodData Central API key (instant signup)

## 4. Backend scope

### Tables (v0.1 subset)
`users`, `goals`, `foods`, `nutrients`, `food_nutrients`, `food_servings`, `log_entries`. (`user_settings` holds only the unit preference for now.) All created through Alembic migrations. Nutrients are rows, so v0.1 seeds just calories, protein, carbs, and fat.

### Endpoints (`/api/v1`)
| Method | Path | Purpose |
|---|---|---|
| POST | `/users` | Create anonymous user, return an ID/token |
| PUT | `/users/me/profile` | Save survey answers, compute and store goal |
| GET | `/goals/current` | Current calorie/macro targets |
| GET | `/foods/search?q=` | Search my saved foods first, then USDA |
| POST | `/foods` | Create a manual food |
| POST | `/log-entries` | Log grams (or serving) of a food for a date |
| GET | `/days/{date}/summary` | Entries plus totals and calories remaining |

The server stores each entry's local date (sent by the phone with its timezone), so "today" is a query, never a reset.

### Pure calculation modules (heavily unit tested)
- **Calorie target:** Mifflin-St Jeor BMR × activity multiplier (1.2 / 1.375 / 1.55 / 1.725 / 1.9), then add or subtract for the goal rate (about 7,700 kcal per kg of body weight). Includes the calorie floor and weekly-rate cap.
- **Unit conversion:** kg/lb, cm/ft-in, g/oz. Stored metric, converted at the edges.
- **Serving to grams:** "1 slice" → grams → nutrients.
- **Nutrient scaling:** per-100 g values × grams, with null kept as "unknown."

## 5. Mobile scope

Screens (minimal, unstyled):
1. **Onboarding:** survey form with unit toggle
2. **Home:** calories target, eaten, remaining; today's entries
3. **Add food:** search box, results, amount + serving picker, manual-entry form

Feature folders keep each area separate, with one typed API client and no screen talking to `fetch` directly.

## 6. CI (GitHub Actions)

**backend-ci.yml** (on every push and pull request)
1. Lint (ruff) and type-check (mypy)
2. Unit tests (pytest)
3. Integration tests against a Postgres service container
4. Build the Docker image

**mobile-ci.yml**
1. Lint (eslint) and type-check (tsc)
2. Unit tests (jest)

Merge rule: branch protection on `main` requiring both workflows to pass.

## 7. Milestones (in order)

Backend and phone work are interleaved: each backend piece gets its phone screen right away, so
problems between the app and the server show up early instead of at the end.

| # | Milestone | Done when |
|---|---|---|
| M0 | Repo + tooling: GitHub repo, folders, README, branch protection | Repo exists, empty CI runs green |
| M1 | Backend skeleton: FastAPI "hello", Docker Compose with Postgres, first migration | `docker compose up` serves `/health`, DB reachable |
| M2 | Calc modules + unit tests | Tests pass for calorie target, units, servings, null handling |
| M3 | Backend: users, profile, goals endpoints | Integration tests pass; goal computed and stored |
| M4 | Phone: Expo skeleton, plus real mobile CI (eslint, tsc, jest) | App on iPhone shows the API's `/health` reply over Wi-Fi; mobile CI green |
| M5 | Phone: onboarding screen against the M3 endpoints | Survey on the iPhone creates a user and shows a sensible calorie target; phone spot-check passed |
| M6 | Backend: foods (manual create, search saved, USDA lookup) | Search returns saved then USDA results; USDA response mapped to per-100 g nutrients |
| M7 | Phone: add-food screen (search, manual entry, amount + serving picker) | Can find or create a food on the iPhone; phone spot-check passed |
| M8 | Backend: log entries + day summary | Totals and remaining calories correct, including timezone date edge cases |
| M9 | Phone: home screen (calories remaining, today's entries) wired to logging | Logging a food on the iPhone lowers "remaining" correctly; phone spot-check passed |
| M10 | Full v0.1 phone checklist (section 8), fixes, CI green | Both gates pass, then tag `v0.1` |

Each milestone is its own branch and pull request.

**M5 scope (as built):** the survey and results screens, the login saved in the iPhone's secure storage, and four quick limitation fixes that came along with it: medical disclaimer text (L2, partly), "prefer not to say" for sex (L3), the goal-weight check plus a weeks-to-goal estimate (L7), and one consistent error format (L19).

**Phone spot-check (every phone milestone, M4 onward).** Before merging, try the new screen on the
iPhone and look for the things only a real phone shows: the keyboard covering a text box, text
running under the notch or home bar, the wrong keyboard type for number fields, awkward scrolling,
buttons too small to tap, and what happens in airplane mode. Anything found is fixed or written
down before the next milestone starts. The full checklist in section 8 is the final gate, and it
should mostly confirm what the spot-checks already caught.

## 8. v0.1 phone test checklist (draft)

On the iPhone 11 via Expo Go:
- [ ] First launch shows the onboarding survey; all fields validate (no empty or impossible values)
- [ ] Switching between metric and imperial converts the displayed values correctly
- [ ] Finishing the survey shows a sensible calorie target on Home
- [ ] Gain/lose/maintain each change the target in the expected direction; an extreme rate is capped or refused
- [ ] Closing and reopening the app skips onboarding and keeps my data
- [ ] Searching a common food (e.g. "banana") returns results
- [ ] Searching a branded food returns results, or I can add it manually
- [ ] Logging 100 g of a food adds the right calories to Home, and "remaining" goes down by the same amount
- [ ] Logging by serving (e.g. "1 bar") gives the same result as the equivalent grams
- [ ] A food I added manually appears in my saved foods and is found first next time
- [ ] Airplane mode shows a clear error, not a crash
- [ ] Changing the phone's timezone or date near midnight doesn't misplace entries
- [ ] Nothing crashes during a 10-minute normal-use session

- Small, descriptive commits.
- Release tags: `v0.1`, `v0.2`, ...

## 10. Risks and notes

- **Phone can't reach "localhost."** The phone talks to the computer's local network IP, so the API address is a config value.
- **USDA data is messy.** Branded foods have inconsistent serving info, so the mapping layer gets thorough tests and unknown values stay null.
- **Expo Go is the testing route.** If something needs a development build (a paid Apple account), we'll find out then and decide.
- **Scope creep.** Anything not listed in section 1 waits for a later version.
