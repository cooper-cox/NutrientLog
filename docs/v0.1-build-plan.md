# NutrientLog v0.1: Build Plan (Draft 4)

Status: in progress (current milestone is tracked in the README). Draft 2 reordered the milestones to interleave backend and phone work (section 7). Draft 3 adds M6.1 and M6.2 (search quality and measure conversion) before the add-food screen; see the plan, section 15. **Draft 4** adds the cleanup milestone M6.R and adopts `engineering-rules.md` (simpler code layout, settings in `config.toml`, security habits for a public repo). Where this file and `engineering-rules.md` disagree, the rules file wins.

## 1. Goal of v0.1

The smallest app that proves the foundations work end to end: **phone → API → database → back to phone**, with the structure everything later will sit on.

**In scope**
- Onboarding survey → calorie target
- Search USDA foods, or enter a food manually
- Log a food in grams or a named serving
- Home screen: "calories remaining" for today
- Anonymous user, data stored in Postgres
- Docker Compose (API + Postgres) and GitHub Actions CI

**Out of scope (later versions)**
Editing/deleting entries, meals, recipes, charts, weight log, AI, workouts, quest, themes, notifications, barcode scan, macros screen.

Note: v0.1 has no workouts, so the "eat back" setting doesn't exist yet. The calorie target is just the base target.

## 4. Backend scope

### Tables (v0.1 subset)
`users`, `goals`, `foods`, `nutrients`, `food_nutrients`, `food_servings`, `log_entries`. (`user_settings` holds only the unit preference for now.) All created through Alembic migrations. Nutrients are rows, so v0.1 seeds just calories, protein, carbs, and fat.

### Endpoints (`/api/v1`)
| Method | Path | Purpose |
|---|---|---|
| POST | `/users` | Create anonymous user, return an ID/token |
| PUT | `/users/me/profile` | Save survey answers, compute and store goal |
| GET | `/goals/current` | Current calorie/macro targets |
| GET | `/foods/search?q=` | Search my saved foods first, then USDA |
| POST | `/foods` | Create a manual food |
| POST | `/log-entries` | Log grams (or serving) of a food for a date |
| GET | `/days/{date}/summary` | Entries plus totals and calories remaining |

The server stores each entry's local date (sent by the phone with its timezone), so "today" is a query, never a reset.

### Pure calculation modules (heavily unit tested)
- **Calorie target:** Mifflin-St Jeor BMR × activity multiplier (1.2 / 1.375 / 1.55 / 1.725 / 1.9), then add or subtract for the goal rate (about 7,700 kcal per kg of body weight). Includes the calorie floor and weekly-rate cap.
- **Unit conversion:** kg/lb, cm/ft-in, g/oz. Stored metric, converted at the edges.
- **Serving to grams:** "1 slice" → grams → nutrients.
- **Nutrient scaling:** per-100 g values × grams, with null kept as "unknown."

## 5. Mobile scope

Screens (minimal, unstyled):
1. **Onboarding:** survey form with unit toggle
2. **Home:** calories target, eaten, remaining; today's entries

## 6. CI (GitHub Actions)

**backend-ci.yml** (on every push and pull request)
1. Lint (ruff) and type-check (mypy)
2. Unit tests (pytest), including a test that loads and range-checks `config.toml` (from M6.R)
3. Integration tests against a Postgres service container
4. Build the Docker image
5. *(from M6.R)* Start Docker Compose, call `/health/db`, shut down (closes L20)
6. *(from M6.R)* Secret scan (gitleaks)

**mobile-ci.yml**
1. Lint (eslint) and type-check (tsc)
2. Unit tests (jest)

**GitHub settings (from M6.R, free on public repos):** secret scanning with push protection, Dependabot alerts (alerts only; no automatic update pull requests), CodeQL code scanning.

Merge rule: branch protection on `main` requiring both workflows to pass.

## 10. Risks and notes

- **Phone can't reach "localhost."** The phone talks to the computer's local network IP, so the API address is a config value.
- **USDA data is messy.** Branded foods have inconsistent serving info, so the mapping layer gets thorough tests and unknown values stay null.
- **Expo Go is the testing route.** If something needs a development build (a paid Apple account), we'll find out then and decide.
- **Scope creep.** Anything not listed in section 1 waits for a later version.
- **Public repo.** Everything committed is visible to everyone. See `engineering-rules.md` section 3. Nothing that grants access is ever committed.
- **Refactor risk.** M6.R touches many files at once, so it changes no behaviour and is judged by identical test results and an identical search report before and after.

**M5.2 follow-up (no separate milestone):** a problem now shows only after you leave a box, never while you are typing in it (the pause-in-typing check was removed), and a bad birth month, day or year is pointed out as soon as that box is left. "Incomplete birth date" waits for the Calculate button. The test timeout was raised to 30 s because a cold CI runner timed out a healthy test, and the test noise (act warnings) was removed.

**M6 (as built):** `foods`, `food_nutrients` and `food_servings` tables (migration 0003). Nutrients are stored as rows keyed by a short name from one catalog (`calc/nutrient_catalog.py`), so adding a nutrient later needs one line and no migration, and a missing row means *unknown*, never zero. `POST /foods` checks a hand-typed food and reports every problem at once; `GET /foods/search` returns the person's saved foods first, then USDA results (minus ones already saved), and a USDA outage never hides the saved results. The USDA reply is turned into per-100 g values by `integrations/usda.py` (units converted, odd or absurd values become unknown, foods without calories are dropped). Outside databases sit behind a small interface, so Open Food Facts (barcodes) can be added later without touching the routes. The USDA field layout is written from USDA's documentation and tested with sample replies; it has not yet been checked against the live service (L35).

**M6 follow-up:** the first phone-free test found that a search like "clif bar" hid specific flavors beyond USDA's first few results. Search now asks USDA for 50 at a time and supports `page=2, 3...` ("show more"), with `usda_has_more` telling the app when more exist. The M7 screen should show a "Show more" button. A second phone-free test showed that asking USDA for foods containing *every* typed word is too strict ("peanut butter clif bar" found one oddly named kit). A thin first page is now topped up with partial matches, best first. All-capital USDA names are tidied without breaking apostrophes ("Kit's", not "Kit'S"), and a brand that just repeats the name is hidden.

**M6.1 (as built):** one search box over several databases. `GET /foods/search` asks USDA and Open Food Facts, merges the same barcode into one product (keeping the fuller record), and ranks everything with one tested scoring function (`calc/food_rank.py`): how many typed words are found in the name *or brand*, whole-food preference for short queries, shorter and more exact names first, the source's own order as a tiebreaker. Every result carries nutrition per serving as well as per 100 g, so the app never does nutrition maths. The response shape changed: `results` (one ranked list), `sources` (who answered), `has_more`. `scripts/search_check.py` runs ~40 real searches and prints a report; the ranking weights are the first thing to tune from it. Not verified against the live services: both mappings were written from documentation (L35, L42).

**M6.1 follow-up (from the first real-data report):** the report showed (1) Open Food Facts failing on most searches, because the check script asked it faster than its limit of about 10 a minute; (2) USDA's plain foods ("Egg, whole, raw") crowded out by thousands of branded products; (3) the same product listed once per package size; (4) messy names and serving labels; (5) community entries with no brand outranking real products. Changes: USDA is searched twice (plain foods and packaged products, in parallel) and the results interleaved; Open Food Facts is a *fallback* asked only when USDA finds fewer than 5 results containing every typed word, is limited to US products, and is retried once after a brief overload; lookalike results (same name ignoring pack sizes, same nutrition and serving) collapse into one; results sharing no word with the search are dropped; half-typed words and one-letter typos still match; a plain-food bonus applies only to curated USDA foods named for what was typed; calories that disagree with protein, carbs and fat (a sign of a database typo) rank lower but are never hidden; names USDA writes twice and servings like "1 ONZ" or "(40g) (40 g)" are tidied. The check script now says PASS or FAIL for each of its 40 searches and waits between Open Food Facts requests.

**M6.1 follow-up 2 (from the second real-data report, 21 of 40 passing):** most failures were service reliability, not ranking: USDA answered "HTTP 400" on about half of searches and Open Food Facts "HTTP 503" on about a dozen. Changes: USDA's error reply is now kept (shortened, never containing the key) and quoted in the report; a passing USDA error (400, 429, 5xx) is asked again after 1 and 3 seconds, and after a 400 the retry leaves out the "Survey (FNDDS)" data type in case that is what USDA objected to; if only one of USDA's two searches (plain foods, packaged products) fails, the other's results are still shown; Open Food Facts is asked up to three times (waits of 2 and 5 seconds); the check script waits 2 seconds between USDA searches (7 for Open Food Facts) and lists what each failing database said. Ranking: a typed plural that only matches a singular ("snickers" against "Snicker Doodle") earns slightly less than an exact word, and no longer counts as a full match; curated names that begin with a category ("Fish, salmon, ..." and "Candies, ..., SNICKERS Bar") now count as named for the food, and the raw/cooked/plain nudge is stronger; the same plain food listed in several USDA datasets ("Broccoli, raw" three times) is shown once; Open Food Facts is also asked for queries of three or more words (a specific product such as "peanut butter clif bar"), because its exact entry (the 68 g, 260 kcal bar) is otherwise hidden by USDA lookalikes. Check script: the Clif searches now require the Crunchy Peanut Butter bar, the Oreo pattern accepts Oreo products, and "chiken breast" is listed as a known gap (L46) instead of a failure. **Linking Strava or another workout app (your question; planned, not built):**
- *Why Strava first:* Apple Watch, Garmin, Fitbit, Wahoo and most phone run/ride apps can already send their workouts to Strava, so one link covers many devices. Linking uses a normal sign-in page (OAuth) that works in Expo Go. Apple Health would be the other big source, but reading it needs native code that Expo Go does not include, so it needs a development build, and Apple's HealthKit permission probably needs the paid Apple developer membership (to be checked); it stays out until then ("free tier always").
- *Strava's rules (from Strava's developer site and a 2026 summary of its agreement; to be read in full before building):* a new app starts in "Single Player Mode" (capacity 1: only the app owner's own data), which is all one person needs; it can be raised to 10 athletes without review and further only after Strava's approval, and Strava's current terms mention a Strava subscription for the Standard tier. Default limits are 200 requests per 15 minutes and 2,000 a day (100 and 1,000 for non-upload calls). Strava's terms bar using its data in AI features, say data is shown only to the athlete it belongs to, and limit how long it may be cached (the summary says 7 days). Those last two rules matter for us: they affect whether imported workouts may be stored permanently, and they block ever showing one person's Strava data to others (any social or quest features). Another reason this stays a "before others use it" decision.
- *How it would work:* Profile screen gets "Connect Strava". The server (not the phone) keeps the tokens and the app's secret in `.env`. Workouts get a `source` ("manual" or "strava") and an outside id so the same activity is never imported twice; a manual workout can still be added for anything Strava does not track (weights, swimming, sports). Strava types map to our activities (Run to Running, Ride to Cycling, WeightTraining to Weight training, and so on). Calories use Strava's own calorie figure when it has one, else our estimate from the moving time. Imports happen when the app opens and on a "Sync now" button (Strava's push notifications need a public web address, which a home computer does not have). If an imported and a manual workout look like the same session (same day and type, similar minutes), the app asks which to keep.
- *Before building:* register a free Strava API app (about five minutes, done by you), read Strava's API agreement's storage and display clauses, and decide with that whether imported workouts are stored or fetched fresh each time.
